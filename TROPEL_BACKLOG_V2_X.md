## §0 · The units problem — one root cause, five wrong numbers

Durations are stored in **µs** internally. Five call sites disagree about that, and they produce contradictory numbers *from the same run*. Fix these together as one audit, not five patches.

- [x] **P0 · `--threshold` / YAML config compare against µs while the docs say ms.** k6-script thresholds are scaled ms→µs (`options.rs:511-528`), but `cli.rs:475-486` and `config_file.rs` pass literals through raw. `--threshold 'http_req_duration.p95 < 500'` compares 500 against ~292 607 → **permanently red**, while the identical threshold inside a script works. `docs/metrics.md:34` advertises the broken form with no unit stated.
  **Done (§0 units audit):** all durations are now stored and compared in **ms end-to-end**; the k6 driver's ×1000 scaling and `DURATION_METRICS` list are deleted, so CLI/YAML/k6-script thresholds all agree in ms. `docs/metrics.md` now states the ms unit.
- [x] **P0 · `handleSummary` / `--summary-export` emit raw µs labelled `"time"`.** `summary.rs:51-64` passes `m.mean/min/p50/...` through unscaled **and** hardcodes `contains: "time"` for every Trend. A run whose stdout correctly prints `p(95)=272ms` exports `"p(95)": 272420` — jslib's `textSummary()` renders that as **4m32s**. Every k6-compatible HTML/JUnit reporter is 1000× off. (`stdout.rs:18-53` was fixed for this; the fix never propagated.)
  **Done (§0 units audit):** summary/export values are ms (the public unit) and `contains` is computed per-metric from the shared time-metric registry (single source of truth), not hardcoded.
- [x] **P0 · Custom time-Trends are stored in ms but divided by 1000 on render.** `driver.rs:1730-1764` pushes the script's raw value with no conversion; `json_stream.rs:200-215` + `stdout.rs:20-53` divide by 1000 for anything registered `isTime` **or** name-matching `duration|_time|latency|ttfb`. `new Trend('api_latency', true); t.add(150)` renders `avg=0.15ms`. Meanwhile the threshold path doesn't scale it, so **the gate and the printed number disagree by 1000× for the same series**.
  **Done (§0 units audit):** ms is the public unit everywhere — emitters push ms, the histogram buckets ms, and no reporter divides. A custom time-trend `t.add(150)` now renders and gates as 150 ms consistently.
- [x] **P1 · `grpc_req_duration` missing from `DURATION_METRICS`.** `options.rs:514-528` lists 13 metrics, none gRPC; the extension records µs (`tropel-x-grpc/lib.rs:535`). Every gRPC `<` threshold is permanently red, every `>` permanently green. Same list contains `ws_session_duration`, which is **never emitted** (the WS ext emits `ws_req_duration`, not a k6 name).
  **Done (§0 units audit):** `DURATION_METRICS` is deleted entirely — durations are ms with no scaling list, so `grpc_req_duration`/`ws_req_duration` thresholds work naturally (the gRPC ext now pushes ms).
- [x] **P1 · `tls_handshaking` and `sending` are hardcoded `Duration::ZERO`** (`types.rs:483-488`) yet are in `DURATION_METRICS` and get ×1000 scaling → `http_req_sending: ['p(95)<10']` is a permanent **false green**.
  **Done (§0 units audit):** no ×1000 scaling exists anymore; these two stay 0 ms (reqwest folds them into connecting/waiting — documented) but are no longer misrepresented by unit scaling.

**Fix:** pick ms as the public unit, convert once at the collector boundary, delete the name-heuristic `/1000` in the reporters, and scale in the CLI/YAML loader as well as the k6 driver.

## §1 · P0 — wrong or empty results

- [x] **P0 · Threshold *stat resolver* fails open, below the validator that fails closed.** The parse layer is genuinely correct (`thresholds.rs:290-348` returns FAIL on bad tokens/operator/RHS, and `validate_thresholds` runs at startup). But the resolver never validates the **stat**:
  - `"http_reqs" => Some(metrics.http_reqs)` (`:551`) **discards the stat entirely** → `http_reqs: ['rate>100']` on a 60 s / 5 000-request run evaluates `5000 > 100` → **PASS** where k6 fails (83 req/s).
  - Unknown/typo'd stat → `_ => d.mean` (`:607`, `:464`, `:541`). `http_req_duration.p95th < 500000` silently gates on the **mean** (180 ms vs a real p95 of 1 200 ms) → PASS.
  - Percentile on a Counter/Rate → hardcoded `0` (`collector.rs:801-838`) → `http_req_failed: ['p(95)<0.01']` **passes on a 100 %-failure run**.
  - Counter per-second `rate` is unimplemented anywhere; `MetricsResult.run_duration` exists and is never read. `data_received: ['rate>1000000']` → per-series mean (~1500) → always FAIL.
- [x] **P0 · Tag-scoped thresholds can never match a real series.** `thresholds.rs:404` builds `{status=200}` and substring-matches, but `collector.rs:85-97` renders one comma-joined group (`http_req_duration{group=http,method=GET,name=…,status=200,url=…}`). The most-copied k6 threshold — `'http_req_duration{status:200}': ['p(95)<500']` — matches nothing → **FAIL with `actual = 0.00` on a healthy run**. The doc directly above the matcher still describes the abandoned key format. Existing tests hand-build single-tag keys.
- [x] **P0 · Unimplemented assertion properties silently pass.** ✅VERIFIED by execution: `pm.expect(false).to.be.true`, `.to.be.null`, `.to.be.undefined`, `.to.be.ok`, `.to.be.empty`, `pm.expect(null).to.exist` all return `undefined` without throwing, and `pm.test` records **green**. Same on the chai prototype for `empty`/`exist`/`NaN`/`finite`. (`pm.js:460-472`, `chai-shim.js:62-100`.) The *implemented* assertions are all correct — the hole is entirely in what's missing, read as a property.
  **Fix:** a `Proxy` `get` trap that throws on unknown assertion names.
- [x] **P0 · Postman collection- and folder-level scripts never run for folder-organized collections.** Three interacting facts in `parser.rs:119,140-144` + `runner.rs:730-742`: folder events *replace* collection events; request events are either/or with parent events (Postman is additive); and `flatten_execution_items` discards a folder that has children, so its script is dead. **A top-level pre-request script that mints a token runs zero times** → every request sends literal `Bearer {{token}}` → 401 across the board, exit 0.
  **Done:** event inheritance is now additive, outer→inner. `convert_items` APPENDS folder events to the inherited chain instead of replacing; `convert_request_item` concatenates `parent_events + req.event` instead of either/or; `find_prerequest_script`/`find_test_script` join ALL matching scripts (`\n;\n`) in chain order. Each leaf carries the full collection→folder→request chain, so flatten's container-drop is harmless — folder scripts run per request exactly as Postman does. Tests: `test_collection_and_folder_scripts_reach_leaves_in_order`, `test_request_scripts_append_to_inherited_not_replace` (parser), and runner-level `folder_leaf_prerequest_runs_and_value_resolves` (minted token persists in `PmState.environment` and resolves via `{{token}}`).
- [x] **P0 · HAR: HTTP/2 pseudo-headers replayed verbatim → 100 % request failure.** `har/lib.rs:308,441-456` copies `:method`/`:authority`/`:scheme`/`:path` into `Request.headers`; `client.rs:584` feeds them to `HeaderName::try_from`, which rejects `:` → builder error → **every request from any modern Chrome HAR fails before a byte leaves the process**. Repo fixtures are hand-written with `"headers": []`, so nothing catches it. Also strip replayed `Content-Length` and `Accept-Encoding`.
  **Done:** new `should_replay_header(name)` filter applied before `merge_headers` in `har_entry_to_item` — drops any name starting with `:` (all four HTTP/2 pseudo-headers) plus `Content-Length`/`Accept-Encoding` (case-insensitive; the client computes content length and negotiates encoding itself). Stripping `:authority` is safe: the client derives `Host` from the URL. Real headers (Authorization, X-Trace, Cookie joins) survive. Test: `test_pseudo_headers_and_replayed_transport_headers_stripped` (mixed-case `accept-encoding` exercises the case-insensitive path).
- [x] **P0 · OpenAPI `$ref` resolution is exponential.** `openapi/lib.rs:908-948` inlines by recursive deep copy and increments `depth` only when a ref is *followed*, not when descending. ✅VERIFIED by simulation: 2 self-refs → 1.18 M nodes; 3 → aborted at 8 M and still growing (k¹⁶). Any spec with `Category { parent, children[], root }` — or any embedded JSON-Schema shape (k≈7 → 3.3×10¹³) — **OOM-kills the process before one request**. The doc claims "cycle-safe … never inlined recursively"; both halves are false. Compounded: the whole document is resolved including `components.schemas` and `responses`, which are `#[allow(dead_code)]` and discarded.
  **Done:** resolver rewritten — memoized + cycle-cut. Only the CONSUMED subtrees resolve (`paths`, `components.securitySchemes`); dead sections clone untouched but refs INTO them from a consumed location still resolve lazily on demand. Each distinct ref resolves ONCE (HashMap cache); an in-progress HashSet cuts cycles with a bounded `{}` placeholder and the placeholder is never cached, so the cache holds only fully-resolved values (self-recursion, mutual A↔B, and pure-self-ref edges all terminate bounded). A recursive body schema now yields a one-level example instead of megabytes/OOM. Tests: `test_recursive_schema_ref_resolves_bounded` (<500-char body), `test_unreferenced_recursive_schema_does_not_blow_up`, `test_deep_ref_chain_still_resolves_fully` (A→B→C inlines fully — memoization caches complete targets, not partial hops).
- [x] **P0 · Worker pool sizes on cumulative VU ids → fd exhaustion → panic swallowed → green run.** `worker.rs:210` does `idx = vu_id % MAX_WORKERS; ensure_workers(idx+1)` where `vu_id` comes from a **process-wide monotonic counter that never resets** (`scheduler.rs:13,498`). 20 cycles of `[{30s,100},{30s,10}]` hands out ~2 000 ids → 2 000 OS threads + 2 000 runtimes + ~4 000 fds at peak concurrency 100. On stock `ulimit -n`, `Builder::build()` → `.expect()` panic inside `spawn_vu` → the scenario task aborts → **`engine.rs:562` discards the `JoinError`** and prints a summary from partial data, exit 0.
  **Done:** the pool now sizes to PEAK CONCURRENCY, not cumulative ids. `spawn_vu` → `acquire_slot` reuses an idle slot (per-worker `Arc<AtomicBool>` busy flag, CAS false→true under the busy mutex), grows one worker only when every slot is busy, and wraps onto an existing worker only past `MAX_WORKERS` (4096). A `BusyGuard` Drop clears the flag on completion OR panic, so slots are reclaimed even when a VU task panics. Also fixed the swallowed-panic half: `engine.rs` now matches the scenario-handle `Err(JoinError)` and counts it as a VU init failure (log + `saturating_add`) instead of silently dropping it — a panicked scenario task can no longer produce a green run. Test: `worker_pool_grows_only_for_concurrent_vus` — 2000 sequential monotonic VUs never grow a 2-worker pool; 3 concurrent VUs grow to 3.
- [x] **P0 · Distributed mode discards script-declared thresholds.** `MetricsSnapshot` has no threshold field; `merge_snapshots` (`controller.rs:178`) uses the *controller's* `JobConfig`. A k6 script's `options.thresholds` are merged only inside the **agent's** engine and never shipped back. `tropel-cloud-run controller --agents 4` with `p(95)<500` breaching at 4 s prints **zero threshold lines and exits 0** — the same run exits 1 locally. A CI gate that evaluates nothing.
  **Done:** `MetricsSnapshot` gained a `thresholds: HashMap<String, ThresholdConfig>` field (Default derive intact); `build_snapshot` populates it from the collector's `effective_thresholds`; `merge_snapshots` overlays each worker's script-declared thresholds onto the controller's job set via `entry().or_insert` (job config wins collisions) **before** `config_needs_histograms`, so script thresholds needing exact percentiles still retain histograms; `absorb_snapshot` inherits thresholds when empty (mirrors trend-stats). - [x] **P0 · WASM AOT cache privacy is asserted, never enforced → arbitrary native code execution.** `wasm/lib.rs:535,542` — both `create_dir_all` and `set_permissions(0o700)` results are discarded, `/tmp/tropel` is never hardened, and nothing re-validates ownership before `unsafe Module::deserialize` (`:499`). The sidecar is an **unkeyed self-hash** (integrity, not authenticity — the attacker writes both halves). With `HOME`/`XDG_CACHE_HOME` unset (systemd units, many CI images), base is `/tmp`; a local attacker pre-creates the dir 0777 and plants `<sha256(source)>.cwasm` + sidecar. Fuel, the 16 MiB cap and import-trapping are all bypassed — the source `.wasm` is never compiled.

New `test_unkeyed_sidecar_forgery_rejected` plants a VALID precompiled module with the old unkeyed sha256 sidecar and asserts the source's plugin id wins (forgery rejected, recompiled, sidecar re-keyed); `test_aot_cache_roundtrip` updated for Option + keyed sidecar + `.cache-key`. 26/26 wasm tests, workspace typechecks, clippy `-D warnings` clean, reviewer signed off after 5 rounds.

## §2 · P1 — major

**Execution / blocking**
- [x] **P1 · Hard-coded 10 s per-iteration JS deadline that `sleep()` and HTTP count against.** `driver.rs:113`, `js_bootstrap.rs:68-71`, `context.rs:255`. The deadline is armed once per eval and is **not** re-armed around blocking host calls (`std::thread::sleep`, `execute_blocking`) — only the WS loop re-arms. `export default function(){ http.get(u); sleep(Math.random()*10); }` — a stock k6 pacing idiom — is interrupted, recorded as a script failure, and **exits non-zero**. Not configurable from CLI or `options`.
  **Done:** blocking host calls now re-arm the per-eval interrupt deadline so the budget measures JS execution time, not wall time. New `tropel_js::rearm_deadline(&AtomicU64, Duration)` stores `now + max_exec` on the same monotonic clock as `reset_interrupt` (the WS loop's inline re-arm was replaced with this shared helper too). Re-arm sites: both `__tropel_native_sleep` bridges (PM `js_bootstrap.rs` + k6 `bootstrap_js_libs`), the k6 `http_request` `execute_blocking`, `http_batch` `execute_blocking`, and the `ws_connect` handshake `execute_blocking` (handle threaded through `register_http_bridges` from `maybe_register_http_bridge`). New `test_sleep_rearms_interrupt_deadline`: 1 s budget + `__tropel_native_sleep(2000)` + `1+1` returns `2` — a sleep longer than the whole budget no longer trips the interrupt. 98/98 k6 lib, 26/26 engine tests, workspace typechecks, clippy `-D warnings` clean, reviewer signed off after 2 rounds.
- [x] **P1 · `gracefulStop` force-stop is advisory only.** The field doc claims VUs check it "in `select!` branches"; grep finds all six reads **between** iterations. `runner.rs:201`'s item loop has no stop check, the JS interrupt is a pure wall-clock deadline never wired to force-stop, `sleep()` is uninterruptible native, and **no VU handle is ever `.abort()`ed**. Detached VUs keep issuing HTTP after the run reports finished (verified path: 30 s duration + `sleep(60)` → traffic until t≈90).
  **Done:** a force-stopped VU now stops **mid-iteration**, not just between iterations. (1) Scheduler: `force_stop_flag()` getter; `await_handles_bounded` **aborts** remaining VU JoinHandles on join timeout (was: warn + detach). (2) tropel-js: `JsContext::new_with_force_stop` links the per-eval JS interrupt to the flag — fires when the deadline passes **or** the flag flips. (3) js_bootstrap: `create_vu_js_context` takes the flag; `__tropel_native_sleep` polls it in 10 ms slices and zeroes the JS deadline on force-stop, so the eval unwinds on resume. (4) runner / vu_sources: `ScenarioRunner.with_force_stop_flag` + item-loop break; a deliberate force-stop no longer counts as a script failure (k6 ends such runs neutrally). (5) sdk: `DriverInstance::set_force_stop_flag` default method (semver-safe). (6) k6 driver: flag field; **the scheduler's flag is polled DIRECTLY through a shared `Arc<OnceLock<Arc<AtomicBool>>>` link cell** (a tokio forwarder task was the original bridge — it is starved while the VU thread is blocked inside the native `std::thread::sleep`, so the sleep ran to completion; the link read is lock-free and adds zero per-VU overhead), plus an eval pre-check and interruptible sleep. Tests: `interrupt_fires_on_force_stop_flag` (tropel-js), `force_stop_flag_breaks_item_loop` (runner), and e2e `force_stop_interrupts_sleeping_vu` (behavior_parity: 2 s duration + 1 s grace + `sleep(60)` script terminates in **3.55 s**, was ~63 s). 106 k6 lib, 23 scheduler, 9 runtime, 7 behavior_parity, workspace typechecks, reviewer signed off.
- [x] **P1 · All VUs share one `reqwest::Client` → one cookie jar.** `vu_loop.rs:505-518` clones an Arc-backed client per VU; `client.rs:198` enables `cookie_store(true)` unconditionally. k6 gives each VU its own jar. A per-VU login writes a session cookie other VUs then send. `no_vu_connection_reuse` is parsed, stored, and **read nowhere** — unimplementable with a shared client.
  **Done:** new `VuCookieClient` (tropel-http) wraps the shared pool client with a per-VU `reqwest::cookie::Jar`; `build_client` no longer sets `cookie_store(true)` (clones of a reqwest::Client share one store+pool — the wrapper is now the sole cookie authority). `HttpClient::execute_with_jar` injects jar cookies per hop (skipped on cross-origin redirect hops and when the request has an explicit `Cookie` header — caller wins) and feeds every hop's `Set-Cookie` into the jar. `DriverHttpClientImpl` (both driver paths + lifecycle/teardown) now wraps `VuCookieClient`. `no_vu_connection_reuse` is now READ: `vu_http_client()` builds a fresh per-VU client (own pool) when set, falling back to the shared client on build error. Regression test `per_vu_cookie_jar_is_isolated_and_persistent` (isolation + persistence against a real mini server). Also fixed a macOS-only worker thread-pinning test flake with a tokio Barrier (both VUs held live so the pool must grow). Verified: tropel-http 57/57, engine lib 27/27, typecheck clean.
