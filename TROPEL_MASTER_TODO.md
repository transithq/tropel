# PART I — INFERENCE

## 1. Where the project actually stands

The last round fixed ~60 items and the fixes are real — nearly every one ships a regression test that reproduces the original symptom, and several tests name the old wrong number in a comment. Whole subsystems came clean: both SigV4 P0s (30 of 34 official AWS `aws4_testsuite` cases now reproduce byte-for-byte), both `tropel-web` wire P0s, all three percentile-fallback paths, the cardinality freeze, the integer-ms floor, k6's absolute-offset ramp table, the control API 6/6, the Postman OAuth-parse P0.

That is not a codebase in trouble. It is a codebase whose remaining problems have **changed category**.

## 2. The three layers, and why they need different treatment

**Layer 1 — a green run can still be wrong.** This is the layer that kills adoption, because a load tester that lies is worse than no load tester. The specific failures are asymmetric and nasty: `pm.test` renames a check on failure so a CI gate reads a series that is *100 % pass by construction*; `pm.response` is never reset after a transport error so tests assert against the **previous** request's 200 — worst exactly at saturation, when `http_req_failed` climbs while `checks` stays green; `.value`/`.last` has three implementations that disagree, one passing vacuously and one failing closed. None of these are exotic. They fire on the most common scripts in existence.

**Layer 2 — the tool caps out an order of magnitude below target, silently.** OTLP is O(n²) *and* ships JSON-not-protobuf with no gzip, needing 140–750 ms of CPU per 100 ms window — **1.4–7.5× oversubscribed, permanently**, capping everything at ~10–30 k samples/s ≈ 1–2.5 k req/s. gRPC hashes the proto *source* (up to 1 MiB) inside a process-global mutex per request, capping at ~1–2 k RPC/s. And there is a live path from a slow output back into the VU hot path: outputs share a **2-thread** runtime with the aggregator, flushes don't yield, the aggregator stops draining, its bounded channel fills in ~1 s, and `record_batch().await` blocks every VU.

Every one of these drops is invisible — all six `Lagged` handlers log at `trace!`, default is INFO, no counter, nothing in the summary. **A user can lose 90 % of their data and see a clean run.**

**Layer 3 — one design decision caps concurrency, and no amount of Layer 2 work moves it.** k6 host functions must be synchronous (they run inside QuickJS `ctx.with` and cannot await), so `execute_blocking` parks the calling VU's OS thread. One VU = one OS thread **plus a full tokio runtime that is structurally idle**. Capped at `MAX_WORKERS = 4096`.

> **In-flight concurrency ≤ 4 096. Throughput ≤ 4096 / mean latency — ~41 k req/s at 100 ms.**
> k6's goroutines cost ~8 KB and never block a thread; 20–50 k VUs per box is routine, putting k6 at **200–500 k req/s**.

Above 4 096 it gets worse, not just capped: `Slot::Wrapped` co-locates 2–3 VUs per thread, `sleep()` is a real blocking sleep, so co-located VUs freeze each other. **A run reporting "10 000 VUs" delivers roughly the throughput of 4 096**, and the summary counts spawned VUs, not effective ones. And memory hits first anyway — 10 000 QuickJS contexts is 10–25 GB, so you OOM before running out of threads.

## 3. HTTP/2 — you have it, and today it is a ~100× regression

`http2` is explicitly enabled, `h2 v0.4.15` is in the lock, `config.http2` defaults `true`, ALPN advertises `h2` first. **Every HTTPS request negotiates h2.**

hyper-util then collapses **all traffic for an origin onto exactly one TCP connection** — a second h2 connection to a known origin is dropped rather than pooled. A server advertising 100 `MAX_CONCURRENT_STREAMS` at 50 ms latency caps you at **2 000 req/s regardless of VU count**, where h1.1 would reach ~200 000.

It is undetectable from inside the tool: no `protocol` tag anywhere, `Response::version()` has **zero call sites**, and `res.proto` is hardcoded `'HTTP/1.1'`. On a multiplexed stream the connector never runs, so `blocked`/`dns`/`connecting` are all 0 and the entire stream-queueing wait lands in `http_req_waiting`, indistinguishable from server latency. (k6 has the mirror bug — it folds h2 queueing into `http_req_sending`. Both wrong, different places.)

## 4. Where tropel is genuinely ahead — protect these

- **HDR histograms.** k6's `TrendSink` retains **every raw observation forever** and sorts under a global lock every 2 s. 10 k RPS for one hour ≈ **2.0 GB** in k6's engine alone. Tropel is O(1) per series, lazily allocated. k6 *has* an HDR impl — wired only to their cloud output.
- **A real cardinality cap.** `MAX_SERIES = 100_000` with drops counted. k6 has none: it warns, **doubles the threshold**, warns again, and the code comment says the process is expected to OOM first.
- **Shared connection pool** — one client per scenario vs k6's per-VU `Transport` + `tls.Config` + `cookiejar` + `Dialer`. At 10 k VUs k6 carries 10 k pools. It also means **TLS session resumption is shared across VUs**, a large unadvertised win from that refactor.
- **Sub-timings at ~1 alloc/request** vs k6's ~14 (`&Tracer{}` + `ClientTrace` + 8 escaping closures + valueCtx + a full `http.Request` copy).
- **`SharedArray`** — native copy + accessor with no per-element `JSON.parse`; k6's re-parses **and** recursively freezes on every element access.
- **`discardResponseBodies`** implemented correctly — it *drains* the body so the pooled connection survives, which most implementations get wrong.
- **mimalloc** already default for the main binary.

## 5. What the reviews say about the code itself

Two observations that should shape how you work, not just what you fix.

**The comments are unusually good, and that has become a liability.** Most non-obvious decisions carry a "why", and several name the exact failure they prevent — that is rare and it is what made these reviews tractable. But **seven comments now describe the intended fix rather than the shipped behaviour** (Digest cache, refcount-1, "k6's exact schema", case-insensitive Cookie, `$ref` bounded, byte-identical bundle, bru store aliasing). A reviewer trusting them signs off on live bugs. I did, twice, and had to re-derive.

**Four tests pin a live bug green.** This is the single biggest reason defects survived five rounds:

| Test | Pins |
|---|---|
| `tropel-auth/lib.rs:1503` | Asserts the **wrong** SigV4 canonical URI (`"/a//b/"` unchanged) |
| `collection/parser.rs:1383` | Hand-writes `protocolProfileBehavior` in the position Postman never uses |
| `metrics/thresholds.rs:1473` | Asserts a threshold passes — it passes because `last` is hardcoded 0 |
| `k6/driver.rs:8945` | Asserts a `#[cfg(test)]` function's contract as if it were production's — see W2 |

> **Rule for this whole plan: every fix ships a test that fails before and passes after, asserting the *user-visible number*, not the internal call. When you touch one of the four above, delete or invert it first** — otherwise the fix looks wrong and gets reverted.

## 6. The bottom line

Fix Layers 1 and 2 and tropel is a correct, fast, honest load tester that beats k6 on memory-per-series, cardinality safety, and observability. **It will still lose on raw concurrency until Layer 3 is addressed**, because 4 096 parked OS threads is a ceiling, not an inefficiency.

Nothing else in the tree structurally prevents beating k6. The allocator is right, HTTP is pooled reqwest/hyper over rustls, tags are `Arc`-interned, histograms are HDR, the AOT wasm cache is real and content-keyed, and the VU/scenario model genuinely matches k6's.

## P · PERFORMANCE AND MEMORY

### P-0 · The headline

> ✅**MEAS** **835,776 bytes of QuickJS heap per VU before a single line of user script runs** — 734,144 of it shims. **7.97 GB at 10 000 VUs.**
>
> **The shims are not lazy-loaded.** One flat concatenated eval, zero gating. An http-only k6 script still pays **291,088 B/VU** for chai + lodash + cryptojs it never touches, plus 255,696 B for `pm.js`.
>
> The bytecode cache is real and *is* taken in production — but it saves **CPU only: −87 % bootstrap time, −2.2 % memory.** `JS_ReadObject` deserializes a fresh copy into every Runtime and `JS_EvalFunction` still materializes the whole object graph per VU. The dominant term is `js_func_size` — compiled function bodies — at 49–57 % of every shim.

**k6 already ran this experiment.** Its core modules are native Go — **0 bytes of library JS per VU**. From their release notes: dropping core-js gave *"a memory drop of about 2MB per VU (from ~2.7MB to ~600KB)"* (v0.31.0), then *"5 times reduction of memory per VU"* (v0.53.0). **Tropel is sitting exactly where k6 was before v0.31.**

### P-H · The structural ceiling — decide before tagging 0.1.0

> **Every HTTP request parks an OS thread for its full duration, capped at 4 096.** ✅**CALC** **Throughput ≤ 4096 / mean latency — ~41 k req/s at 100 ms.** k6: **200–500 k**.

- [ ] 4 096 `enable_all()` current-thread runtimes ≈ **4 096 epoll instances and ~8 192 fds before a single socket**, plus 4 096 timer wheels — and each per-VU runtime is **structurally idle**, since the VU's future is its only task and it immediately parks the thread.
- [ ] Per request: a channel allocation, a boxed task spawn, **two cross-thread handoffs**, and past the 40 µs spin a park/unpark futex pair. **The doc comment itself estimates ~200 k syscalls/s at 100 k rps.** k6 does **zero** cross-thread handoffs.
- [ ] To be fair to the code: the spin-then-park heuristic with the `SKIP_SPIN` thread-local is well-designed and correctly bounded. **The problem is that the bridge exists at all**, because host calls must be synchronous.
- [ ] **Escaping it requires an async QuickJS host-call path (Promise-returning host functions + job-queue pumping) or a fiber VU model.** That is a redesign. **It is not an optimization — it is the thing that decides whether tropel can beat k6 at concurrency.** Doing it also collapses the thread-per-VU pool into ordinary tokio tasks, removes the 8 GiB stack reservation and 8 200 fds, removes the `MAX_WORKERS` ceiling, and unblocks the shared-Runtime memory option.
- [ ] **Above 4 096 VUs you don't get the VUs you asked for, and nothing says so.** `Slot::Wrapped` co-locates VUs (`worker.rs:339`) and `sleep()` is a real blocking sleep, so they freeze each other. ✅**MEAS** at 10 000 VUs: workers 0–1 807 host **3 VUs each**, 1 808–4 095 host **2**. With `http.get(); sleep(1);` a 3-VU worker **triples** each VU's iteration period. **A run reporting "10 000 VUs" delivers roughly the throughput of 4 096.** *Report achieved concurrency, or warn loudly when wrapping begins.*
- [ ] **Memory hits first anyway** — `MAX_WORKERS` caps threads at ✅**MEAS** 4 096 × 44.8 KiB = **183 MiB**, but **not `JsContext`s**: all 10 000 VUs build their own QuickJS context = **10–25 GB**.
- [ ] **Second, *fixable* cap: one single-threaded aggregator on a 2-worker runtime.** ~9 samples × 100 k rps = ~900 k samples/s into one task that also stops dead 100–200 ms every 2 s. *Shard by metric-name hash.* No redesign needed.

### P-C · Mechanical perf — post-release, high volume of small wins

- [ ] **`merge_scenario_tags` erases the entire `Arc<TagMap>` design under one line of user config.** `vu_loop.rs:994-1005` uses `Arc::make_mut` with the comment *"cheap here: the fresh per-request Arc has refcount 1."* **The runner does the exact opposite, deliberately** — `runner.rs:549-551` shares one Arc across ~12 samples with the comment *"bump a refcount instead of copying the whole map."* So `make_mut` sees refcount 12, 11, 10 … and **deep-clones eleven times per request**; only the last mutates in place.
